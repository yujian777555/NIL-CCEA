## 二、研究主线：不得偏题

工作名称：**NIL-CCEA — Noise-aware Interaction Linkage Cooperative Co-evolution for LLM Agents**。

研究对象是由多个可替换模块构成的 LLM Agent。核心科学问题是：在 Agent 执行噪声下，如何估计模块之间可重复的非加性交互，学习带符号和不确定性的 linkage 结构，并让合作协同演化利用该结构搜索更好的模块组合。

演化计算必须是方法主线。预期算法闭环是：

1. 对模块进行受控干预，测量成对模块的非加性交互；
2. 估计交互强度、方向/符号和不确定性；
3. 构建可按任务族条件化的 signed linkage graph；
4. 根据 linkage 结构决定独立变异、协同变异或兼容性约束搜索；
5. 随种群和任务分布变化更新 linkage，并在固定总评估预算下与强基线比较。

**固定总预算是公平比较条件，不是本项目的创新主线。不要把研究方向改写成评价预算分配、候选评估调度或一般性 Agent 提示词优化。** 也不要把项目改成只做模块消融、普通 GA 或模型微调。

目前所有机制仍是待验证假设。不得把算法名称、设计草图或文献差异直接写成已成立的创新点。

## 五、Phase 0B：Benchmark 与环境兼容性审计

### 5.1 候选环境

### 5.2 必须验证的属性

对每个候选环境检查并记录：

- 许可证、访问条件、依赖、运行方式和维护状态；
- task ID、task version、task family 是否稳定；
- 环境状态是否可重置，seed 是否真实控制环境随机性；
- Agent 执行过程是否暴露完整工具轨迹和终止状态；

- 工具权限、外部服务依赖、速率限制和潜在 API 成本；
- 是否能在同一 task/state/seed 下配对运行不同配置；
- 是否能独立替换模块而不改变其他模块、工具权限或评分逻辑；

### 5.3 四个模块必须做真实兼容性检查

当前暂定模块槽位：

- Planner：任务分解与行动计划；
- Selector：候选工具/动作/计划步骤的选择；
- Caller：工具参数构造、调用执行和错误处理；
- Synthesizer：结果整合与最终回答。

这些名称和边界是暂定的。必须通过真实代码调用链确认它们是否可以独立替换。特别检查 Selector 与 Caller 是否职责重叠、Planner 是否能被外部注入、Synthesizer 是否会读取隐藏评测信息。

如果 benchmark 不支持四个独立模块：
- 不得伪造模块边界；
- 不得通过只改一个大 prompt 却声称完成四模块独立干预；
- 给出可行的替代模块划分及证据；
- 说明模块数变化后 factorial 配置数如何变化（m 个二元模块为 2^m）；

## 七、Phase 0D：冻结测量协议并构建最小运行器

现有初始协议是四个二元模块的 2^4 = 16 配置。只有在四模块独立替换被证实后才使用该设计。

### 7.1 运行器必须支持

- 配置生成和唯一 configuration_id；
- 模块变体 ID、内容哈希和不可变 manifest；
- task/seed 配对及环境 reset；
- 运行前配置完整性检查；
- 原始 episode 记录和轨迹引用；
- 每次调用、失败、重试、token/API 成本和总预算账本；
- 失败状态显式记录，不允许静默删除；
- 缓存键包含 task/version、环境 seed、模块哈希、模型/provider/version、解码设置和 runner 版本；
- 分析结果可从原始 episode 数据重新生成；
- 每次运行绑定 source commit、config hash 和协议版本。

### 7.2 统计协议

- 主终点必须是 benchmark 原生、预先指定的指标；候选可为 task success。
- 次要指标可包括工具调用有效性、约束违规、token/API 成本、延迟和执行步数。
- 对每一对模块计算 difference-in-differences 交互对比，并对其他模块配置求平均。
- 以 task instance 为聚类单位估计不确定性；不能把同一 task 的重复 episode 当成独立样本。
- 预先指定实用效应阈值 delta、多重比较校正和缺失/失败处理。
- 报告任务族异质性、交互符号、置信区间和敏感性分析。
- 二阶交互不代表不存在三阶或更高阶交互；如数据提示 pairwise linkage 不足，设计独立诊断，不要事后隐瞒。

现有计划为 12 tasks × 2 environment seeds × 16 configs = 384 episodes。这只是计划值，不是必须照搬的固定样本量。先根据可用任务数、方差、成本和功效/敏感性分析评估；只能在正式冻结前调整，调整必须记录理由。不得看过确认性结果后再改样本量、终点或阈值。

### 7.3 运行顺序

1. 先完成纯 mock/dummy 模块测试，不产生真实 API 成本；
2. 完成配置完整性、接口、reset、配对、缓存、失败和成本账本测试；
3. 运行 2 tasks × 1 seed × 全部配置的 smoke test；
4. smoke test 通过并经独立审查后，才申请正式 pilot；
5. 若正式 pilot 需要付费 API 或外部服务，先提交成本估算、调用上限和停止条件，取得用户明确批准后再启动；
6. 本阶段不进行基模微调、LoRA、训练式模块更新或 A800 训练实验。

## 八、重要：出现零交互、弱交互或失败时如何继续

**不得因为某一对模块没有显著交互、某一任务族结果不理想、某个 benchmark 不兼容或某轮 smoke test 失败，就直接宣布整个方向不可行并停止。**

按顺序诊断：

1. 操作检查：两个模块变体是否真的改变了预期行为，是否有足够机制差异；
2. 测量检查：日志、评分器、配对和 reset 是否正确；
3. 噪声检查：执行随机性、模型波动、工具失败和环境状态是否掩盖效应；
4. 任务检查：任务是否真正依赖相关模块组合，是否存在任务族异质性；
5. 功效检查：当前样本是否有能力识别预设的实用效应；
6. 表达检查：是否遗漏三阶交互、非线性兼容关系或条件化交互；
7. 环境检查：当前 benchmark 是否提供了足够的模块干预空间。

如需追加诊断实验，必须形成单独版本的诊断协议，清楚标记探索性/确认性数据，不得把探索性结果伪装成预注册确认结果。保留所有零结果、失败结果和原始轨迹。目标是找到可验证的提升机制，而不是人为制造正结果。

同时注意：检测到交互并不等于 NIL-CCEA 能提升搜索。后续必须在相同总 Agent-execution budget 下，与独立模块变异、随机分组、固定分组、非 linkage cooperative co-evolution 等公平基线比较；探测、失败调用和重试全部计入预算。
